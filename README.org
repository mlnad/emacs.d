* Overview
This is a highly customized Emacs configuration designed for efficient coding,
writing, and project management.

** Key Features
- Modular Design: The configuration is organized into logical sections, making
  it easy to navigate and modify.

- Dynamic Code Generation: Org-mode tables and Babel blocks are used to
  dynamically generate Emacs Lisp code, reducing redundancy and improving
  maintainability.

- Extensive Customization: Variables, keybindings, and package configurations
  are tailored to optimize workflows for coding, writing, and project
  management.

- Modern Tools: Integration with modern Emacs packages like Eglot (for LSP),
  Vertico (for completion), and Magit (for version control) ensures a
  cutting-edge development experience.

- Cross-Platform Support: The configuration is designed to work seamlessly
  across different operating systems, with specific adjustments for Windows,
  Linux, and macOS.

** Mono-file
All the configurations for start Emacs is integrated into [[file:init.org][init.org]]. These codes
can be tangled into ~init.el~ and ~early-init.el~ by =org-babel-tangle=.

* Installation
1. Clone this repository:
   #+begin_src shell
   git clone https://github.com/mlnad/moyu-emacs.git ~/.emacs.d
   #+end_src

2. Install dependencies:
   #+begin_src shell
   sudo apt install ripgrep fd-find tree-sitter
   #+end_src

3. Start Emacs - packages will be automatically installed

* Health check
=moyue doctor= verifies that the configuration files are complete and correct:
=init.org= / =init.el= are present, =elpa/= is populated, =.cache/env.el= is
readable Lisp, and the declared fonts are well formed. It also probes the
external programs the configuration delegates work to, one check per program:
=config/tool-*= for the command-line tools (git, grep, find, ripgrep, fd, the C
toolchain, latexmk, uv, ruff, ty, ...) and =config/lsp-*= for the language
servers eglot would start (rust-analyzer, clangd, ty, ruff, gopls, ...). A
missing required tool fails the run; a missing optional one -- a language
server for a language you do not edit, say -- is reported as =SKIPPED= instead.
Add =EMACS_TEST_VERBOSE=1= to see
the install hint of every program a check could not find.

It runs the checks built into [[file:bin/moyue.el][bin/moyue.el]] and exits non-zero if any of
them fail. Without a selector every =config/= check runs; a bare word selects the
checks whose name contains it, so the two families can be run on their own:
#+begin_src shell
bin/moyue doctor                            # every config/ check
bin/moyue doctor tool                       # the command-line programs
bin/moyue doctor lsp                        # the language servers
bin/moyue doctor config/emacs-version       # a single check
EMACS_TEST_VERBOSE=1 bin/moyue doctor lsp   # with the install hints
#+end_src

The unit tests for the =lisp/= helpers, [[file:bin/moyue.el][bin/moyue.el]] and the =bin/commands/=
extensions are a separate concern and run with =moyue test=. With no argument it
runs every test outside the =config/= namespace; a pattern is an ERT selector
read as Lisp, so a regexp needs quotes of its own:
#+begin_src shell
bin/moyue test                                    # everything except config/
bin/moyue test '"^treesit-"'                      # tests whose name matches a regexp
bin/moyue test core/insert-file-path-inserts-filename   # one test, by name
#+end_src

(The =config/= checks are defined only by =moyue doctor=, so =moyue test= cannot
select one of them: run =bin/moyue doctor config/emacs-version= instead.)

* Tree-sitter grammars
Grammar libraries are pinned to exact upstream revisions, compiled into
=~/.emacs.d/.cache/tree-sitter/=, and built from sources kept in
=~/.emacs.d/.cache/tree-sitter/src/<lang>/=.

The cache is searched before =~/.emacs.d/tree-sitter/= and before the system
library directories, so a grammar built there is always the one Emacs uses,
while a grammar that has not been built yet falls back to whatever else
provides it. Nothing ever compiles an upstream default branch on its own:
built-in grammar downloading is switched off, and the revision to build comes
from the pinned manifest in [[file:bin/commands/treesit.el][bin/commands/treesit.el]] -- a command-line
concern, so =init.el= only declares where to look and loads no library.

Because the sources are kept, a grammar can be edited by hand and recompiled.
=moyue treesit build= compiles whatever revision is on disk; it never resets
the checkout. =moyue treesit reset= is what restores the pinned revision.

#+begin_src shell
bin/moyue install --grammars          # check out and build every pinned grammar
bin/moyue treesit status              # pin, source and library state
bin/moyue treesit sync                # fetch the pins, then build (network)
bin/moyue treesit build bash python   # rebuild selected grammars (offline)
bin/moyue treesit update --write      # move the pins to newer releases
bin/moyue treesit verify              # prove the whole chain, exits non-zero
#+end_src

=verify= checks, for every pinned grammar, that the checkout sits on its pin,
that the library exists, that Emacs can load it, that the ABI it reports is the
one the pinned source declares (which is what catches a silent fallback to a
distribution package), and that the font-lock rules bundled with Emacs still
compile against it. The last check matters because a grammar whose node types
have moved on keeps loading, it only loses highlighting behind a warning.

=install= only touches grammars when asked, so the default path stays offline
and takes seconds; without =--grammars= it just says how many are pinned. A
checkout that already carries local edits is never reset by either command.

Which modes use tree-sitter is left to Emacs: =init.el= sets
=treesit-enabled-modes= to =t=, so the whole of Emacs 31's
=treesit-major-mode-remap-alist= (C, C++, CMake, CSS, Dockerfile, JSON, Python,
Bash, YAML, Java, Ruby, TOML, Lua, HTML, JavaScript, TypeScript, C#, PHP, Go
and more) routes to tree-sitter. Note that this has to be =setopt= and not
=setq=, and it has to run after =treesit= is loaded: the variable installs its
value through a =:set= function that fills =major-mode-remap-alist=, and =setq=
skips that function -- the setting would read back as =t= while no ts-mode was
ever enabled. HTML files land in =mhtml-ts-mode=, which is the pair Emacs ships
and which also drives the embedded CSS and JavaScript grammars.

* External tools
=moyue install= sets up the configuration; =moyue install TOOL= sets up the
programs the configuration delegates work to. Each tool is described once, by
an entry of =moyue-tool-recipes= in [[file:bin/commands/tools.el][bin/commands/tools.el]], and that same
entry is what =moyue doctor= turns into a =config/tool-*= or =config/lsp-*=
check -- so a program this command can install is exactly one whose absence
doctor reports.

#+begin_src shell
bin/moyue install --list                 # what can be installed
bin/moyue install clangd clang-format    # named tools
bin/moyue install --all                  # every recipe
bin/moyue install ruff --version 0.16.10 # pin a release
bin/moyue install ruff --dry-run         # only print what would happen
bin/moyue tools status                   # what is installed, what is missing
bin/moyue tools remove clangd --force    # delete the package and its bin/ entry
#+end_src

Three shapes cover every recipe:

- =:strategy single= -- one self-contained executable. It is downloaded into
  =.cache/pkgs/<tool>/<version>/= and copied into =bin/=, which =init.el= keeps
  at the front of PATH, so nothing else needs configuring. =clang-format= is
  installed this way, from the static builds published by
  [[https://github.com/cpp-linter/clang-tools-static-binaries][cpp-linter]].
- =:strategy archive= -- a tarball or zip with more than one file. =clangd= is
  the reason this exists: its executable needs the clang headers beside it
  under =lib/clang/<major>/=, so the tree is unpacked into =.cache/pkgs/= and
  only a relative symlink is left in =bin/=. clangd derives its resource
  directory from the path of its own executable, and a symlink still resolves
  there, so the bundled headers are found with no wrapper script.
- =:strategy installer= -- the vendor ships an install script, which is what
  =uv=, =ruff=, =ty= and =rustup= do. The script is downloaded into the
  package cache first and run from there, so it can be inspected and is never
  piped straight from the network into a shell. =uv=, =ruff= and =ty= install
  into =~/.local/bin= (or into =bin/= when that is not writable, as in a
  sandbox), =CARGO_HOME= and =RUSTUP_HOME= stay at their usual =~/.cargo= and
  =~/.rustup=, and rustup's =rust-analyzer= component is added afterwards. The
  variables that stop a script from editing shell startup files
  (=*_NO_MODIFY_PATH=1=) or updating itself behind our back
  (=*_DISABLE_UPDATE=1=) are set by the recipe.

Versions are reproducible: =:version= pins a fallback, the newest release is
used only when it can actually be resolved (offline runs fall back to the pin),
and =--version VERSION= overrides both. Downloads and their unpacked payloads
stay below =.cache/pkgs/=, which =.gitignore= already excludes; the few
entries this command adds to =bin/= are listed there too.

* Python
Python buffers are edited with the built-in =python-ts-mode= and driven by
three programs from [[https://astral.sh][Astral]], each one installed by =moyue install TOOL=
and reported by =moyue doctor=:

| Tool | Role                      | Check               |
|------+---------------------------+---------------------|
| uv   | interpreters, the =.venv= | =config/tool-uv=    |
| ty   | language server (eglot)   | =config/lsp-python= |
| ruff | linter and formatter      | =config/tool-ruff=  |

#+begin_src shell
bin/moyue install uv ty ruff     # the Python toolchain
bin/moyue doctor lsp             # what eglot would start
#+end_src

The activation itself lives in [[file:lisp/python-ext.el][lisp/python-ext.el]].  It finds the project
root (=project-current= first, then the nearest =pyproject.toml=, =uv.lock=,
=requirements.txt=, =setup.py=, =setup.cfg= or =Pipfile=), takes the nearest
=.venv= that actually carries an interpreter, and sets it up buffer-locally:
=python-shell-virtualenv-root=, =VIRTUAL_ENV= and the front of =exec-path=.
eglot, apheleia, flymake and =run-python= therefore all reach the interpreter
and the tools the project pinned, two projects never fight over =exec-path=,
and a remote workspace keeps using the tools of the host that owns its files.

The uv commands run from the project root, whatever directory the buffer is
in, and are bound to =C-c u= in both Python modes:

| Key     | Command                   | What it runs              |
|---------+---------------------------+---------------------------|
| =C-c u s= | =moyu/python-uv-sync=   | =uv sync=                 |
| =C-c u l= | =moyu/python-uv-lock=   | =uv lock=                 |
| =C-c u a= | =moyu/python-uv-add=    | =uv add PACKAGE...=       |
| =C-c u r= | =moyu/python-uv-run=    | =uv run COMMAND...=       |
| =C-c u R= | =moyu/python-uv-run-file= | =uv run= the current file |
| =C-c u i= | =moyu/python-uv-init=   | =uv init DIRECTORY=       |

=C-c u R= also runs a PEP 723 script: uv reads the inline metadata the file
carries and builds the environment it names.

* Tempel templates
Tempel keeps its templates in one lisp-data file, =templates=, next to
=init.el=: the local templates merged with every template data file of
[[https://github.com/Crandel/tempel-collection][Crandel/tempel-collection]],
where a name that exists in both is taken from the collection. Tempel does not
diagnose a file that breaks that format -- a template group without a mode is
dropped in silence, and an element its reader cannot consume hangs
=tempel--file-read= outright -- so =moyue check-templates= reads the file the
same way and names the offending form instead:
#+begin_src shell
bin/moyue check-templates                        # the configured templates file
bin/moyue check-templates FILE                   # an explicit file
bin/moyue check-templates .cache/tempel-collection/templates  # every *.eld
#+end_src

A =DIR= argument checks every =*.eld= file directly inside it, which is the
layout the collection uses, so a checkout below =.cache/= can be validated
whole. The command exits non-zero when any file fails, which makes it usable as
a gate. Two checks go past the collection's own =scripts/check-templates.el=:
data after the first Lisp form (what unbalanced parentheses look like) is an
error instead of being ignored, and a template name defined twice for one mode
is reported, because =tempel-expand= can only ever reach the first of the two.
The implementation is [[file:bin/commands/templates.el][bin/commands/templates.el]].

* Docker
The [[file:Dockerfile][Dockerfile]] builds a lean base image (Emacs + git + a C toolchain)
for three distributions; the configuration itself is never baked in, it is
mounted at run time.

| Distribution | Base image         | Emacs package |
|--------------+--------------------+---------------|
| archlinux    | =archlinux:latest= | =emacs=       |
| ubuntu       | =ubuntu:latest=    | =emacs-nox=   |
| alpine       | =alpine:latest=    | =emacs-nox=   |

Arch Linux is the default everywhere.

** dockemacs
=Dockerfile= is driven by =bin/dockemacs=: build an image, run Emacs
interactively, or run the integration test suite inside it.
#+begin_src shell
bin/dockemacs build [DISTRO]                   # build moyue-base:DISTRO
bin/dockemacs run   [DISTRO]                   # run terminal Emacs in that image
bin/dockemacs itest [DISTRO|all] [--rebuild]   # install + test inside the image
bin/dockemacs distros                          # list the supported distributions
#+end_src

=itest= builds =moyue-base:DISTRO= on first use, then mounts the checkout
read-only at =/mnt/emacs.d=, copies it into a writable tmpfs at
=/root/.emacs.d= and runs =moyue install= + =moyue doctor= there, so the
host tree is never modified:
#+begin_src shell
bin/dockemacs itest                # archlinux
bin/dockemacs itest ubuntu
bin/dockemacs itest alpine --rebuild
bin/dockemacs itest all            # every distribution, in order
#+end_src

Extra Docker arguments can be injected through the environment, which is useful
behind a proxy or on a restricted network:
#+begin_src shell
DOCKEMACS_BUILD_ARGS="--network=host" bin/dockemacs build ubuntu
DOCKEMACS_RUN_ARGS="--network=host"   bin/dockemacs run ubuntu
#+end_src

=MOYUE_ITEST_BUILD_ARGS= and =MOYUE_ITEST_RUN_ARGS= are accepted as legacy
aliases for the two variables above.

The images carry what =moyue install TOOL= needs on top of the Emacs
toolchain: =curl= for the vendor install scripts (uv, ruff, ty, rustup) and
=unzip= for clangd's release archive. =alpine= exercises the busybox =wget=
path and the musl platform keys, which is where the two distributions differ
most. Note that clangd publishes no musl build: =moyue install clangd= says
so on Alpine and points at =apk add gcompat=, while ruff, ty, clang-format
and the Rust toolchain all install there normally.

* Customization
It will automatically create a =~/.emacs.d/.cache/userconfig= file to override
the default settings.

* Environment variables
Emacs started from a desktop launcher or a systemd unit does not inherit the
login-shell environment. =moyue install= therefore captures it once into
=~/.emacs.d/.cache/env.el=, an ordinary Emacs Lisp file:

#+begin_src emacs-lisp
(setenv "PATH" "/home/user/.emacs.d/bin:/usr/local/bin:/usr/bin:/bin")
(setenv "GOPATH" "/home/user/go")
#+end_src

The file is loaded on every Emacs startup. =~/.emacs.d/bin= is always placed at
the front of =PATH=, so the configuration's own commands (=moyue=, =dockemacs=,
…) are available; add further directories with =M-x moyu/add-to-path= (which also
saves them to the file), or by setting =moyu/env-extra-path=. The file is only
generated when missing, so manual edits are kept across later =moyue install=
runs. Use =moyue install --force-env= or =M-x moyu/reload-env= to regenerate it
from the shell, and =M-x moyu/env-visit-file= to open it for editing.
